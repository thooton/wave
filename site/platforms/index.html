01 / USB GUIDE

Before you connect.

Check the model in Settings → About phone: XP3800, Android 8.1. Other XP3 phones are not interchangeable. The site checks Android compatibility and verifies saved backups. An optional build can also read a boot backup over USB. Nothing here flashes or restores the phone.

Keep a way back

Back up contacts, messages, photos and other personal files. A stock boot image is not a copy of your personal data. Keep two copies of the untouched image off-device, along with the original SHA-256, serial and firmware build. Do not use an image from another phone, even one of the same model.

Computer and cable

Use a data cable and USB port you trust, and close other tools holding the device. An HTTPS page in a WebUSB-capable desktop browser such as Chrome or Edge can request a USB device; check the site and device before approving. Firefox and Safari do not supply that API. USB is not needed for the app setup generator.

All platforms

Only one program can use a USB interface at a time. Before using the page, stop the desktop adb server (adb kill-server) and close other phone or service tools. Use Chrome or Edge; Firefox and Safari have no WebUSB. The XP3800 shows up twice: as an Android debugging device (1d9c:8339) while Android runs, and as Qualcomm EDL (05c6:9008) in service mode. WebUSB asks you to choose a device again each time it changes.

Linux

Use the distribution’s Android udev rules for the debugging interface (lsusb shows the IDs). For EDL, these two narrow rules let a logged-in desktop user open only 05c6:9008 and keep ModemManager from probing it:

# /etc/udev/rules.d/70-wave-xp3.rules
SUBSYSTEM=="usb", ATTR{idVendor}=="05c6", ATTR{idProduct}=="9008", TAG+="uaccess"
SUBSYSTEM=="usb", ATTR{idVendor}=="05c6", ATTR{idProduct}=="9008", ENV{ID_MM_DEVICE_IGNORE}="1"

Ask the system administrator to reload udev rules (udevadm control --reload) and reconnect. Do not make every USB device world-writable or disable ModemManager system-wide.

A kernel driver may already hold the EDL interface. Chromium takes over a few drivers itself (cdc_acm, usblp, ftdi_sio and usb-storage) but not others. On the test machine the qcserial module, which is aliased to 05c6:9008, was loaded and the interface was bound to a kernel driver, so Chromium could not claim it until that driver was detached. We detached it with libusb (pyusb detach_kernel_driver) before the page connected; reading the bound driver’s name directly was not done. If the page says it cannot claim the interface, an administrator can stop qcserial from binding for the session: unbind that interface under /sys/bus/usb/drivers/, or run modprobe -r qcserial before connecting. A permanent fix is blacklist qcserial in /etc/modprobe.d/. These administrator commands are untested here, and removing qcserial affects any other Qualcomm modem you use.

05c6:900e is a crash-dump interface, not the service interface.

Windows (untested)

WebUSB only sees a USB interface that uses the WinUSB driver. In EDL the phone normally binds Qualcomm’s serial driver (shown as “Qualcomm HS-USB QDLoader 9008” under Ports), which Chrome cannot open. The documented fix is to bind WinUSB to that one device with Zadig:

  1. Put the phone in EDL (05c6:9008) and leave it connected.
  2. In Zadig, choose Options → List All Devices and select the entry whose USB ID is 05C6 9008. Stop if the ID differs or several entries match.
  3. Choose WinUSB as the target driver and click Replace Driver.
  4. Reload the page and select the device.

This replaces the driver for that device only; never replace the driver of a composite parent, a hub or hardware shared with something else. To undo, open Device Manager, uninstall the device and tick “delete the driver software”, then reconnect. After the replacement, desktop service tools that expect the Qualcomm serial driver will not see the phone until you undo it. For the Android debugging interface (1d9c:8339), Windows may also need a vendor or Google USB driver bound to WinUSB; follow the same Zadig steps for that interface, and check which interface you select.

macOS (untested)

Chrome and Edge reach vendor-specific USB interfaces without a driver, so no Zadig-style step is expected. The usual obstacles are another program or the adb server holding the interface, a charge-only cable, or a browser policy that blocks WebUSB. If a kernel extension or another tool has claimed the EDL interface, quit it before connecting.

ChromeOS and Chrome on Android (untested)

These support WebUSB but no device flow has been tried. Chrome on Android with a USB-OTG cable could work without a computer, which is worth testing separately.

Protect debugging access

USB debugging lets an authorized computer run commands on the phone. Only approve a fingerprint for your own computer. When done, disable debugging and revoke authorizations you no longer use in Developer options.
